# 生产级核心接口压测基线

## 范围

- 环境：当前宿主机本地部署
- 日期：2026-04-25
- 目标：建立控制面接口性能基线，识别推理链路阻塞项，并沉淀统一业务指标与验收标准

## 压测方法

- 控制面接口：`120` 请求，`20` 并发，`15s` 单请求超时
- 工具：Python 标准库线程并发压测脚本
- 指标口径：
  - `success_rate`：2xx/3xx 成功率
  - `rps`：总请求数 / 总耗时
  - `avg_ms`：平均延迟
  - `p50_ms` / `p95_ms` / `p99_ms`：分位延迟
  - `max_ms`：最大延迟

## 关键发现

- Go 控制面接口表现稳定，`p95` 小于 `60ms`，可作为当前平台性能标杆。
- Python 管理接口可用性正常，但延迟明显偏高，`p95` 接近 `800ms`。
- `30000/api/models` 通过 Nginx 代理到 Python 后，`p95` 上升到约 `2.07s`，存在明显尾延迟放大。
- `3000/api/models` 当前匿名访问返回 `401 Unauthorized`，不能直接作为匿名压测目标。

## 推理链路探测

### 探测结果

- `POST http://127.0.0.1:35001/v1/chat/completions`
  - 单请求、`max_tokens=8`
  - `45s` 超时未返回
- 因单请求基线未通过，本轮未继续对推理接口做并发压测，避免对运行模型造成额外风险

### 结论

- 当前推理链路不满足生产级压测前提
- 在修复推理超时问题前，只能将控制面指标纳入正式基线

## 业务指标定义

### A. 平台可用性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 控制面可用率 | `/health`、`/api/health`、`/manage/models` 成功率 | `>= 99.9%` |
| 推理可用率 | `/v1/chat/completions` 成功率 | `>= 99.0%` |
| 网关健康可用率 | `/health` on `3000` 成功率 | `>= 99.9%` |

### B. 控制面时延指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| Go 健康检查 `p95` | `/health` on `35001` | `<= 100ms` |
| Go 模型列表 `p95` | `/v1/models` on `35001` | `<= 100ms` |
| Python 管理查询 `p95` | `/manage/models` on `35000` | `<= 800ms` |
| 前端代理管理查询 `p95` | `/api/models` on `30000` | `<= 1000ms` |
| 网关健康检查 `p95` | `/health` on `3000` | `<= 150ms` |

### C. 推理业务指标

| 指标 | 定义 | 建议目标值 |
|------|------|-----------|
| 首字返回时间 `TTFB p95` | 小请求下从发起到首 token 返回 | `<= 3s` |
| 小请求完成时间 `p95` | `max_tokens <= 32` 的同步请求 | `<= 15s` |
| 超时率 | 超过接口超时阈值的请求占比 | `<= 0.1%` |
| 推理错误率 | 非 2xx 响应占比 | `<= 1.0%` |

### D. 资源与稳定性指标

| 指标 | 定义 | 建议目标值 |
|------|------|-----------|
| 健康分 `health_score` | 平台综合健康分 | `>= 95` |
| GPU 显存利用率 | 主卡显存占用率 | `<= 92%` 持续运行 |
| 队列积压 | `/manage/queue` 中待处理请求 | 稳态下不持续增长 |
| 尾延迟放大比 | 代理入口 `p95` / 直连后端 `p95` | `<= 1.5` |

## 规范化验收标准

### 1. 分层压测口径

- `L1 直连后端`：`35000`、`35001`
- `L2 前端代理`：`30000`
- `L3 网关入口`：`3000`
- 同一接口必须至少保留一组 `L1` 与一组 `L2/L3` 数据，才能评估代理损耗

### 2. 测试分级

| 级别 | 场景 | 负载建议 |
|------|------|---------|
| `Smoke` | 发布后可用性确认 | `n=20, c=5` |
| `Baseline` | 日常基线留档 | `n=120, c=20` |
| `Stress` | 容量边界探索 | 逐步抬升并发，直到错误率或延迟越界 |

### 3. 验收规则

- 任一控制面接口成功率低于 `99.9%`：不通过
- 任一 Go 控制面接口 `p95 > 100ms`：告警
- Python 管理接口 `p95 > 800ms`：告警
- 前端代理到 Python 的接口 `p95 > 1000ms` 或尾延迟放大比 `> 1.5`：不通过
- 推理链路单请求超时：阻塞生产级压测与发布验收

## 当前结论

- 控制面：
  - Go 侧达到生产可用水平
  - Python 管理接口可用但存在明显优化空间
  - 前端代理到 Python 的模型列表尾延迟过高，当前不满足建议目标
- 推理面：
  - 单请求超时，当前判定为 `P0` 阻塞项

## 后续建议
